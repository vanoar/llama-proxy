# llama-proxy

Лёгкий прокси для llama.cpp на сервере, где в GPU помещается только одна модель за раз.
Прокси **полностью притворяется llama-server**: слушает тот же порт, прокидывает все
запросы как есть и управляет загрузкой моделей по полю `"model"` в OpenAI-совместимом API.

**Модели и параметры их запуска задаются в JSON-конфиге** — сколько угодно штук,
параметры можно менять без пересборки, конфиг перечитывается на лету (SIGHUP).

Логика:

- при старте сразу загружается **первая модель из списка** (или `default_model`,
  если задан); `"default_model": "none"` отключает автозагрузку совсем;
- `"model"` в запросе совпал с алиасом модели (регистр не важен) →
  если модель уже стоит в памяти — просто прокидываем; если стоит другая —
  **сначала дожидаемся завершения всех in-flight запросов к текущей модели**
  (свитч не прерывает идущую генерацию), потом SIGINT текущему llama-server
  (как Ctrl+C: корректное само-завершение), поднимаем нужную
  **с параметрами из конфига**, ждём готовности (поллинг `/v1/models`)
  и только потом прокидываем запрос; запросы пришедшие во время ожидания
  копятся в очереди
- один Go-бинарь (~6.8 МБ), ноль зависимостей, только стандартная библиотека,
  типовое потребление ~5–10 МБ RAM

## Файлы

| Файл | Назначение |
|---|---|
| `main.go` | прокси: конфиг, свитч моделей, проксирование |
| `dashboard.go`, `dashboard.html` | дашборд на `/` и его API `/_admin/api/*` (страница встроена в бинарь) |
| `monitor.go` | сбор метрик для дашборда: CPU/RAM/температуры/GPU/llama-server |
| `logtail.go` | хвост лога llama-server и журнал запросов для дашборда |
| `config.json` | конфиг: пути, таймаут и список моделей |
| `dist/llama-proxy` | собранный бинарь под **linux/amd64** (static) |
| `llama-proxy.service` | unit для systemd |

Пересобрать бинарь на сервере (если есть `go`):
`go build -trimpath -ldflags="-s -w" -o llama-proxy .`

Проверить конфиг без запуска: `./llama-proxy -check -config config.json`
(печатает решённые модели, ненулевой exit code при ошибке).

## Конфиг (`config.json`)

```json
{
  "listen_addr":  ":8080",              // где слушает прокси (по умолчанию :8080)
  "backend_addr": "127.0.0.1:8081",     // где крутится управляемый llama-server (по умолчанию 127.0.0.1:8081)
  "llama_bin":    "./llama.cpp/build/bin/llama-server", // путь к бинарнику
  "cwd":          ".",                  // рабочий каталог для llama-server
  "load_timeout": "15m",                // максимум времени нагрузки модели
   "default_model": "Qwen3.8-27b",       // модель для старта; не задан -> первая в списке; "none" -> не грузить
  "nvidia_smi":   "",                   // дашборд: путь к nvidia-smi; "" -> из PATH; "none" -> не опрашивать GPU
  "backend_ui":   "",                   // дашборд: ссылка на web-UI llama-server; "" -> http://<хост из адреса страницы>:<порт backend_addr>/
  "models": [
    {
      "name": "Muse-Glimmer-30B",       // каноническое имя (его отдаёт /v1/models и /_admin/status)
      "aliases": ["Muse-Glimmer-30B", "muse"],  // значения поля "model" в запросах (регистр не важен)
      "env": { "GGML_OP_OFFLOAD_MIN_BATCH": "2048" },
      "args": [
        "-hf", "unsloth/Muse-Glimmer-30B-GGUF:UD-Q6_K_XL",
        "-c", "500000", "-n", "32000",
        "--temp", "1.0", "--top-p", "0.95", "--top-k", "64",
        "-ctk", "q8_0", "-ctv", "q8_0",
        "--host", "0.0.0.0", "--metrics"
      ]
    },
    {
      "name": "Qwen3.8-27b",
      "aliases": ["Qwen3.8-27b", "qwen"],
      "env": {
        "GGML_CUDA_ENABLE_UNIFIED_MEMORY": "1",
        "MTMD_BACKEND_DEVICE": "none",
        "GGML_OP_OFFLOAD_MIN_BATCH": "2048"
      },
      "args": [
        "-hf", "unsloth/Qwen3.8-27B-GGUF:UD-Q8_K_XL",
        "-c", "262144", "-n", "32000",
        "--temp", "1.0", "--top-p", "0.95", "--top-k", "20", "--min-p", "0.0",
        "-ctk", "q8_0", "-ctv", "q8_0",
        "--host", "0.0.0.0", "--metrics",
        "--spec-type", "draft-mtp", "--spec-draft-n-max", "4",
        "--chat-template-kwargs", "{\"preserve_thinking\":true}"
      ]
    },
    {
      "name": "Qwen3.8-Flash-Next",
      "aliases": ["Qwen3.8-Flash-Next", "qwen-flash", "flash"],
      "bin": "./llama.cpp/build-mmq/bin/llama-server",  // свой бинарник (опционально), иначе глобальный llama_bin
      "env": {
        "LLAMA_QSA_NATIVE": "1",
        "MTMD_BACKEND_DEVICE": "none",
        "GGML_OP_OFFLOAD_MIN_BATCH": "1024"

        "-hf", "unsloth/Qwen3.8-Flash-Next-GGUF:UD-IQ4_XS",
        "-c", "262144", "-n", "32000",

        "-ctk", "q8_0", "-ctv", "q8_0",
        "--host", "0.0.0.0", "--metrics",
        "-b", "8192", "-ub", "1024", "--cache-reuse", "256",
        "--chat-template-kwargs", "{\"preserve_thinking\":true}"
      ]
    }
  ]
}
```

Правила:

- `args` — это ровно argv llama-server (массив строк, без шелла). Прокси
  **добавляет** `--port <backend_addr>` и отбрасывает случайный `--port` из конфига.
- `bin` (в модели, опционально) — путь к бинарнику **конкретно этой модели**;
  переопределяет глобальный `llama_bin`. Для моделей без `bin` используется
  `llama_bin`. Полезно, когда модель нужна из отдельной сборки (например
  `build-mmq` для QSA-моделей, остальные — из `build`).
- Все поля верхнего уровня и `env`/`aliases`/`bin` необязательные (пустые `env`/`aliases`
  = нет). `aliases` можно не писать — тогда работает `name`.
- Алиасы не должны повторяться между моделями (с учётом регистра) — конфиг
  отклонится с ошибкой, что видно и по `-check`, и в логах.
- **Третья (N-я) модель** — просто ещё объект в `models`.
- `default_model` — алиас/имя: при старте прокси сразу поднимет эту модель.
  **Если не задан — грузится первая модель из `models`**, т.е. после старта
  прокси сразу готов отвечать без ожидания загрузки. `"default_model": "none"`
  (регистр не важен) возвращает старое поведение: старт лёгкий, модель
  загружается по первому запросу.
- `--host 0.0.0.0` в конфиге бэкенда оставлен как в оригинале — бэкенд слушает
  `backend_addr`'s port на всех интерфейсах. Не нужен снаружи → замени на `127.0.0.1`.

## Установка на сервере

Прокси запускает llama-server сам, поэтому сначала **останови ручной llama-server**
(порт 8080 займёт прокси, 8081 отдаётся бэкенду).

```bash
# 1. Скопируй на сервер: binaрь, config.json, unit
# 2. chmod +x llama-proxy
# 3. sudo cp llama-proxy.service /etc/systemd/system/
#    sudo systemctl daemon-reload
#    (в unit поправь User / WorkingDirectory / пути — помечено "ВАЖНО")
# 4. sudo systemctl enable --now llama-proxy
#    journalctl -u llama-proxy -f    # логи (сюда же попадает log llama-server)
```

## Горячая перезагрузка конфига

`sudo systemctl reload llama-proxy` (или `kill -HUP <pid>`) перечитывает
`config.json` **без перезапуска и без разрыва уже подтянутых запросов**:

- изменённые `env`/`args`/`aliases`/`backend_addr`/`llama_bin`/`load_timeout`/
  `default_model` применяются сразу;
- модель, которая уже стоит в памяти и **поменялась** в конфиге, переподнимется
  с новыми параметрами при следующем запросе к ней; если не менялась — не переподнимется;
- `listen_addr` требует перезапуска (`systemctl restart llama-proxy`);
- при ошибке в новом конфиге старый остаётся в силе (видно в логах).

## Флаги бинаря

| Флаг | По умолчанию | Описание |
|---|---|---|
| `-config` | `config.json` | путь к JSON-конфигу |
| `-check` | `false` | проверить конфиг и напечатать решённые модели, затем выйти |

## Служебные эндпоинты

| Эндпоинт | Ответ |
|---|---|
| `GET /` | дашборд (HTML) |
| `GET /health` | `llama-proxy ok` (прокси жив; модель может ещё не быть загружена) |
| `GET /v1/models`, `GET /models` | список всех моделей из конфига |
| `GET /_admin/status` | `{"current":"Qwen3.8-27b","backend_pid":1234,"up_seconds":5678}` |
| `GET /_admin/api/stats` | всё, что показывает дашборд, одним JSON |
| `GET /_admin/api/logs?after=N` | хвост лога llama-server (последние 300 строк, инкрементально) |
| `POST /_admin/api/switch` `{"model":"qwen"}` | загрузить модель (мягко: ждёт активные запросы) |
| `POST /_admin/api/unload` | выгрузить модель, освободить VRAM |
| `POST /_admin/api/force` | не ждать активные запросы в текущем свитче/выгрузке (обрывает их) |

POST-эндпоинты `/_admin/api/*` принимают только `Content-Type: application/json`
(чужая страница в браузере не сможет дёрнуть их без CORS-preflight). Отдельной
авторизации нет — как и у самого API: кто достучался до порта, тот и
переключает модели.

## Дашборд

Открой `http://<сервер>:8080/` в браузере:

- **Модель** — что загружено, сколько времени, контекст/слоты/билд (из `/props`);
  список моделей конфига с кнопкой «Загрузить», «Выгрузить модель»; во время
  свитча — фаза (ждём N активных запросов / загрузка) и кнопка «Не ждать»;
  последняя ошибка (упал llama-server, не загрузилась модель).
- **Скорость** — генерация сейчас (ток/с по всем слотам, из `/slots`) с графиком;
  последний запрос: промпт и генерация (токены, ток/с, время) и доля принятых
  draft-токенов (MTP/спекулятивка) — берётся из строк `print_timings` лога
  llama-server; средние с момента загрузки — из `/metrics`.
- **Задачи** — сколько слотов обрабатывают промпт / генерируют, очередь
  llama-server (`requests_deferred`), запросы, ждущие в прокси (свитч модели),
  таблица слотов.
- **GPU** — загрузка, VRAM, питание, температура, вентилятор, частоты, P-state
  каждой карты (`nvidia-smi`).
- **Процессор, память, температуры** — загрузка CPU (общая и по потокам), load
  average, ОЗУ/swap, CPU и RSS процесса llama-server, сеть, все датчики hwmon.
- **Запросы через прокси** — активные и последние 40: статус, ожидание в
  очереди, длительность, объём ответа.
- **Лог llama-server** — хвост лога (в т.ч. прогресс скачивания `-hf`),
  опрашивается только пока блок раскрыт.
- Кнопка **«Web UI llama-server ↗»** — ссылка на встроенный UI бэкенда (порт 8081).

**Нагрузка.** Пока страницу никто не смотрит, дашборд не делает ничего.
Метрики снимаются только по запросу открытой вкладки и не чаще раза в ~1 с
(все вкладки получают общий кэшированный снимок); скрытая вкладка опрос
останавливает. CPU/RAM/сеть/температуры — чтение `/proc` и `/sys/class/hwmon`
(`/proc/cpuinfo` читается один раз при старте; `drivetemp` пропускается, чтобы
не будить HDD). GPU — один долгоживущий `nvidia-smi --query-gpu … -lms 2000`,
который запускается при открытии дашборда и гасится через ~45 с после
закрытия. llama-server опрашивается через `/slots` и `/metrics` — лёгкие
служебные задачи, генерацию не тормозят. Средние скорости требуют `--metrics`
в args модели (он уже стоит в примерах); без него дашборд покажет остальное.
Учти: `/metrics` llama-server обнуляет «оконные» гейджи
(`prompt_tokens_seconds` и т.п.) при каждом чтении — если по `:8081/metrics`
ходит ещё и свой Prometheus, эти два гейджа у него станут шумнее (счётчики
`*_total` не страдают).

## Как это работает

1. **Маршрутизация.** В POST-запросе читается JSON-тело и поле `"model"`.
   Имя мапится на модель конфига по алиасам (регистр не важен).
2. **Свитч.** Нужная модель ≠ текущей → прокси **ждёт завершения всех
    in-flight запросов к текущему бэкенду** (мягкая остановка: идущая
    генерация/стрим не прерывается; прокси видит это по своим коннектам —
    закрыт ответ от бэкенда = запрос закончен), затем текущему llama-server
    SIGINT (аналог Ctrl+C: процесс сам чисто завершается, грейс 15 с,
    затем SIGKILL), старт нужной по конфиге, поллинг `/v1/models`
    до готовности, затем прокидка запроса. Запросы к другой модели,
    пришедшие во время ожидания/свитча, стоят в очереди.
    Если клиент обрывает запрос, стоящий в очереди, он просто отбрасывается
    **без** переключения модели (иначе мёртвые запросы + ретраи клиента
    бесконечно гоняют модели туда-сюда).
    Запрос учитывается в in-flight счётчике, **пока ещё не отпущен lock на
    свитч** — иначе следующий запрос из очереди видел бы «свободный» бэкенд
    и резал модель за миллисекунду до того, как только что подошедший
    запрос начал стримить (502 + ретраи = вечный пинг-понг моделей).
    Клиенту всё это выглядит как один длинный ответ.
    Ошибка загрузки → клиенту `503`.
3. **Прозрачность.** Всё остальное (заголовки, тела, SSE-стриминг, ошибки)
   прокидывается как есть. Поле `"model"` в запросе подставляется реальным id,
   который сообщает сам бэкенд (новые llama.cpp 404'ят на несовпадающее имя),
   т.е. клиенту ответ придёт с тем же `"model"`, что запросил.
4. **Без лишнего.** Пока модель не меняется, каждый запрос — чистое
   реверс-проксирование (тело читается целиком ради извлечения `"model"`,
   ответы стримятся по мере прихода).

### Краевые случаи

- **Нет имени модели + ничего не загружено** (например `GET /props` в начале,
  при `default_model: "none"`) → `503` с подсказкой; любой запрос с `"model"`
  сам загрузит модель. По умолчанию (и при явном `default_model`) модель уже
  стоит с момента старта.
- **Неизвестное имя модели** → `404 unknown model ...` со списком доступных.
- **llama-server упал сам** (OOM, сбой GPU) → следующий запрос снова поднимет модель.
- **Чужой llama-server** уже слушает `backend_addr` при старте → прокси его
  "принимает", но убить не сможет; свитч упадёт с ошибкой. Убей вручную:
  `pkill llama-server`.
- **Параллельные запросы к разным моделям** выполняются последовательно:
  свитч начинается после завершения активных генераций текущей модели,
  остальные запросы ждут в очереди (TCP-коннект при этом держится).
  Запрос к **той же** модели, что уже загружена, свитч не трогает и
  прокидывается сразу (бэкенд сам держит параллельные слоты).

## Замечания

- **Таймауты клиентов.** Свитч = перезагрузка модели: от десятков секунд до
  пары-тройки минут. HTTP-клиенту нужен длинный таймаут, иначе при первом
  запросе после свитча он "оборвётся" — это нормально.
- **Мягкая остановка при свитче.** Прокси не убивает идущую генерацию:
  переключение модели ждёт, пока завершатся все активные запросы к текущей
  модели. Осторожно: зависший «вечный» стрим будет блокировать свитч
  бесконечно — чтобы форснуть переключение, прервите зависшее клиентское
  соединение (llama-server сам отменит такой ген-слот) или перезапустите
  прокси.
- Только **Linux** (SIGINT/SIGKILL/SIGHUP). Windows-сборки для прода не intended
  (тамошняя graceful-остановка — SIGKILL после 15 с, т.к. Go на Windows не умеет
  шлать SIGINT в чужой процесс).

## Тесты

- `go test ./...` — юнит-тесты: валидация конфига, алиасы, дубли, `default_model`
  и модель, грузимая при старте (первая в списке / `none`),
  сборка argv (подмена `--port`), семантика SIGHUP-reload (unchanged-модель не
  переподнимается, изменённая — да, битый конфиг не применяется).
- E2E с фейковым llama-server: `/health`, `/v1/models`, `/props`, свитчи в обе
  стороны, повтор без перезагрузки, SSE-стриминг, 404/503, `/_admin/status`,
  проверка, что каждая модель реально стартует со **своими** argv из конфига.
